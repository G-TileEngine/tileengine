## Rules
### A. Hand pose: `clips[].points.hand_pose` (item 1; EA ruling b)
1. **Shape.** `points.hand` stays `([x, y] | null)[]` **exactly as today** (project-format §6.2 line 433). The pose is a new optional per-frame array beside it, **`points.hand_pose: ({angle?, z?} | null)[]`**: entry `f` is the pose on clip frame `f`. It holds only angle and z, never a position, so the hand position keeps one home. `null`, `{}` or an absent field = the defaults (angle 0, z from the facing default). Absent `hand_pose` = defaults on every frame.
2. **Length.** A 1-entry list means "same pose on all frames" (as `points`). Shorter than `frames.length`: the missing frames read as defaults, **no warning** (unlike `points`, a short pose list does not pad with its last entry). Longer: warns **`clipPointsInvalid`** once per clip; the extra entries are kept and ignored. `hand_pose` is independent of `hand`: a frame with a pose but no hand point uses today's hand fallback (`centre`) with that pose.
3. **`angle`.** Degrees, clockwise on screen (y down), measured from straight up: the direction the held item's head points on that frame. 0 = straight up. Read mod 360. Any finite JSON number is legal (fractions too).
4. **`z`.** `"front"` draws the item as `fxFront`, `"behind"` as `fxBehind`, relative to the swinging unit. **Absent = the facing default:** `"behind"` while the unit faces up (N), else `"front"`, the same rule as `depth_by_facing` / `faceSwap` (setup-format line 816, fx-player.ts:105). The default follows the unit's facing at play, not the clip name, so a §7.3 fallback clip still gets the right default.
5. **Per facing and mirroring.** Like `points.hand`, each facing clip has its own `hand_pose`, and a mirrored clip uses its source clip's (project-format line 433, §7.3 step 2). On the mirrored (left) side: `x' = fw − 1 − x` for the hand point (unchanged), **`angle' = −angle` (mod 360)**, and the item's picture is drawn mirrored, so its base angle becomes `−held.angle`. **`z` is not mirrored.** `noMirror: true` (line 437) stops mirroring as today.
6. **Checks (warn, never block; EA ruling a).** An unknown `z` string warns **`outOfRange`** at `clips[i].points.hand_pose[f].z`, is kept, and plays the facing default. A wrong JS type (a non-number `angle`, a non-string `z`, an entry that is neither an object nor `null`, or a non-array `hand_pose`) warns **`clipPointsInvalid`**, is kept, and reads as the defaults. Unknown keys inside an entry are kept and ignored. **Not H2:** H2 covers answers, overrides and unit stats (project-format line 1672), and every AssetMeta clip check is a warning.
7. **Older builds.** A reader that predates this CN keeps `hand_pose` on save and ignores it (the keep-and-ignore it already applies to an unknown point such as `points.foot`, with `clipPointsInvalid` at most). **`points.hand` is untouched, so older builds still draw the hand and anchor effects on it exactly as today.**
8. **Writer.** Writes `hand_pose` only when some frame has a non-default pose: `null` for default frames inside the list, `angle` omitted when 0, `z` omitted unless the maker flipped it, trailing default entries trimmed. Clearing every pose removes the key (absent).

### B. The impact frame is `contact` (item 2)
9. **Reuse `contact`; `impact` is a read alias only.** `clips[].events` already has `contact` (project-format line 432): the first `contact` in time feeds `hitAt`, it is derived when no events are stored, and `start_on: "contact"` (setup-format line 811) already starts an effect on it. A second name would be a duplicate source of the same frame. `impact` is also already taken as the effect knob "Impact burst" (`effect.impact`, toggle, catalogue rev 7), so a clip event `impact` would collide in maker wording and in search. The Studio may **label** the tick "Impact"; the stored name is `contact`.
10. **Alias (EA ruling c).** A stored event named `"impact"` reads as `contact` and is kept as stored (never rewritten). **At load, every stored `"impact"` event read as `contact` gets an info line `clipEventAliasRead`** (PROPOSED name) naming the asset, clip and frame ("'impact' read as 'contact'"). The writer writes `contact`.
11. **One per motion.** The contact frame fires the action, the prop hit and `start_on: "contact"` effects. If a clip has more than one `contact` (aliases included), the **first in time** wins, as today (same frame: stored order). All entries still fire as named events (sound), as today. On a clip used as a `tool-swing` motion only, the extras warn **`clipContactDuplicate`** (PROPOSED name) once per clip. Other clips get no new note, so old projects report nothing new.
12. **Derived contact.** With no stored events the derived contact (biggest pose change, else `floor(n / 2)`) still applies. It may not be the intended hit; the editor shows "Set the impact frame" as info. Not a warning.

### C. Held item on the item's art (item 3)
13. **`held` on AssetMeta**, kinds `sprite` and `image`: `{grip: [x, y], angle?: number}`. `grip` is in whole art px from frame 0's top-left (the item is one still frame). `angle` is the item's **base angle**: degrees clockwise from straight up, the way the item's head points as painted (e.g. 45 for a pickaxe painted pointing up-right). Absent = 0.
14. **Draw.** On each frame of the motion clip the item is drawn with `grip` on that frame's hand point, rotated about `grip` by `hand_pose[f].angle − held.angle`, on layer `hand_pose[f].z` (defaults per rules 1–4). With no hand point (absent or `null`) it uses today's fallback (`centre`) with that frame's pose.
15. **Visibility is runtime, not stored.** The item shows from frame 0 of the motion clip and hides after its last frame; never idle or walking (CEO 19:48). No idle or walk sockets, no stored visibility flag.
16. **Checks.** `held` missing on an asset an item swings: grip = the asset's `anchor`, angle 0, info **`heldMissing`** (PROPOSED). `grip` not a pair of whole numbers inside the frame, or a wrong JS type on `angle`: **`heldInvalid`** warning (PROPOSED), kept, the field reads as absent. Not H2 (rule 6). `held` on another kind (`tileset`, `background`, `page`, `audio`): kept and ignored silently.
17. **Which asset an item swings** is the item definition's job (35a item defs: `{id, tags, asset}`), not this CN's. This CN only fixes that the art's grip and base angle live on that asset's `held`.

### D. Swing bindings (item 4)
18. **Home.** A new catalogue behaviour **`tool-swing`** (L53). The binding table is its list knob **`bindings`**; the prop rows are its list knob **`props`** (part E). Stored as an ordinary setup (`setups/<setupId>.json`, `behaviourId: "tool-swing"`) referenced from `project.rules`, and replaced per stage by a stage `rules` setup or a stage override of the whole list (setup-format §2.9: one value, one home). Undo, presets and Godmode come for free. Not a project-root key, not in AssetMeta, not in `CoreMapObject`.
19. **Row.** `{id, label, item_tag, motion, target_tags, action}` (setup-format §2.9 list item: `id` `[a-z0-9][a-z0-9_-]{0,31}`, `label` 1–48 chars). The EA's working names `itemTag` / `targetTags` / `actionId` are the catalogue's snake_case `item_tag` / `target_tags` / `action`; they were never stored, so no alias is needed.
    - `item_tag`: one item tag (`pickaxe`, `hoe`, `axe`, `sword`, `tool`, `weapon`, or a maker tag). **Forward ref (EA ruling f):** item tags come from 35a item definitions, which have no format yet. Until they land, a tag no item carries is info **`unknownRef`** (never H2) and the row simply never matches. A wrong JS type is still H2.
    - `motion`: a clip **action** name (§6.3 naming `<action>-<facing>`), e.g. `"overhead"`, `"side"`, `"thrust"`, `"use"`, `"cast"`; or a list of 2–4 of them, which **alternates** per swing per unit, starting at index 0 (sword "Alternate" = `["overhead", "side"]`). The swing-side counter is runtime rules state, not stored here.
    - `target_tags`: tags of what the swing may hit. `[]` = any target. **Not checked against tile types or prop tags (EA ruling e):** until C2a defines the tag sets, an unknown tag is inert (it just never matches) and gets no warning.
    - `action`: a rules action id (presets use `mine`, `plough`, `chop`, `hit`). Action ids are rules data, registered in `src/rules` (TSa / 35b / C2a), never in `src/core`.
20. **Target tags of the faced cell** (checked in this order; the first that exists is the target): a living unit on the cell → `["unit"]`; else the map object on the cell whose `prop` names a `props` row → that row's `tags`; else the cell's terrain tile-type id as one tag (e.g. `dirt`). `unit` is reserved for units.
21. **Match: first match in stored order.** The rules take the held item's tags and the target's tags, and use the **first** row whose `item_tag` is one of the item's tags and whose `target_tags` is empty or shares a tag with the target. No specificity scoring: order is the maker's priority, and the editor adds new maker rows above the preset rows. **Shadowing (EA ruling g):** when an earlier row matches every swing a later row could (same `item_tag`, and the earlier row's `target_tags` is `[]` or a superset of the later row's), the editor warns **`bindingShadowed`** (PROPOSED name) on the later row, naming the earlier one. Warning only; both rows are kept. No matching row: if the item has any row, the swing plays that item's first row's motion with no action (a prop target gets the wrong-tool "tink", no progress); if the item has no row, nothing plays ("Pick a tool" hint is UI).
22. **Dangling and bad values (warn, never block).** An `action` no rules slice registers warns **`unknownRef`** at `bindings[i].action`, is kept, and the swing plays with no action. A `motion` naming no clip resolves through §7.3 steps 1–3, then `attack` (steps 1–4), with the existing clip-fallback report. A `motion` list over 4 warns `overCap` and keeps all. A wrong JS type (non-string `item_tag` / `action`, non-array `target_tags`) or a missing `id` / `label` / duplicate `id` is **H2 `invalidValue`** (setup-format §2.5, §2.9; this is answer data; EA ruling a).
23. **Presets (catalogue default of `bindings`, item-first).** Ordinary default items, **not** `reserved_ids`, so makers can delete or reorder them (no `reservedMissing` re-adding):

| `id` | `item_tag` | `motion` | `target_tags` | `action` |
|---|---|---|---|---|
| `pickaxe-mine` | `pickaxe` | `"overhead"` | `["rock", "ore"]` | `mine` |
| `hoe-plough` | `hoe` | `"overhead"` | `["dirt"]` | `plough` |
| `axe-chop` | `axe` | `"side"` | `["tree"]` | `chop` |
| `sword-hit` | `sword` | `["overhead", "side"]` | `["unit"]` | `hit` |

`tool` and `weapon` get no default row (the maker picks Motion and Hits, UX §1). **Hoe (EA ruling e):** it targets `dirt` only, the built-in walkable tile type (catalogue rev 23, L45). C2a will add `soil` (and any ploughed-state tag) to this row when it defines ploughable ground; until then target tags are not checked against tile types. These ids are frozen: a deleted preset id is never reused for another meaning.

### E. Prop rules rows (item 5)
24. **Row.** `tool-swing.props` item `{id, label, tags, hits_to_finish, reacts_to?, yields}`.
    - **No `asset` field (EA ruling d).** A prop row is found from the map placement, not from the art (next rule).
    - `tags`: target tags (`rock`, `ore`, `tree`, …). `unit` here warns `outOfRange` and is ignored, so a prop is never a unit target.
    - `hits_to_finish`: slider 1–6, step 1, **default 3** (CEO). Out of range warns `outOfRange`, kept, and plays as stored (values below 1 play as 1). Not a whole number: `offStep`, plays rounded.
    - `reacts_to`: item tags that make progress. **Absent = derived:** any item whose binding row targets this row's `tags`. `[]` = reacts to nothing (indestructible, always "tink"). An item not in `reacts_to`: wrong-tool tink, no progress.
    - `yields`: a loot-table id (35a loot tables) or `null` = drops nothing. Default `null`. **Forward ref (EA ruling f):** 35a loot tables have no format yet, so an id that names no table warns **`unknownRef`** (never H2), is kept, and drops nothing. A wrong JS type is still H2.
25. **Placement ref: `objects[].prop?` (EA ruling d).** A map placement becomes a prop by naming a `tool-swing.props` row `id` in the new optional field **`prop`** on the map's `MapObject` (project-format §6.4), beside the existing per-placement `lightSource?` and `motion?` (lines 1011–1012). The ref sits on the placement itself, whose `id` is a stable placement id (line 1009: `[a-z0-9][a-z0-9_-]{0,31}`, unique within the map; `CoreMapObject.id` is marked STABLE, core-types.ts:77). So it survives any repaint or re-id of the art, and it is deleted with its placement, so a stale ref can't attach to a new object.
    - **Why not by asset.** Asset ids are content hashes (line 444), names are free text, and there is no redirect map. The only carry-forward is editor ref-rewriting on re-id (recipe edit line 518, bake line 649, "Update from library" line 717, migration 005 line 1585), whose listed targets are project.json, maps, units, stages and `bakedFrom`, **not setup answers**. A plain re-upload of new art makes a new asset with no rewrite at all, and no rewriter exists in code yet (`/tmp/ede4` `src`: none). An asset-keyed row would silently stop matching after a repaint.
    - **Not core.** The core map reader keeps only `id`, `at`, `footprint` and `blocks` (`/tmp/ede4` `src/project/read/map.ts:19–27`, `objectOf`). Like `assetId`, `lightSource` and `motion`, `prop` never reaches `CoreMapObject`. TSa reads it through the project map document, not core. `map` stays **v5**; absent = today.
    - **Checks.** A `prop` that names no row in the stage's effective `tool-swing.props` (including a stage with no `tool-swing` setup) warns **`unknownRef`**, is kept, and the object plays as today's plain object. A non-string `prop` warns the same (map placement fields are warn-only, as `lightSource`); `null` = absent. Many placements may share one row.
    - **Editor.** The prop sheet edits the row. "Apply to every object with this picture" is a writer convenience that writes `prop` on each matching placement (one op per map). The row stays the one home for hits, tags, reacts-to and yields.
26. **Never on `CoreMapObject`.** Hits to finish, progress, reacts-to and yields live only on this rules row and in rules state (`propHit {objectId, at, progress, done, wrongTool?}`, engine-side §2). `CoreMapObject` stays occupancy-only, so core-types does not change and E5's CN-022 core-types wait is untouched. A map object with no `prop` is exactly today's object.
27. **Progress is runtime rules state**, not map data. Where it persists (session save, cozy C8a) is that CN's business; no progress is written into `maps/<id>.json` (only the static `objects[].prop` ref lives there). The done state (felled, broken, ploughed) is a rules-driven frame or asset swap (C2a), not a format key here.
28. **Wrong JS types** on `props` items (non-array `tags` / `reacts_to`, non-number `hits_to_finish`, non-string non-null `yields`) and bad `id` / `label` are **H2 `invalidValue`**, as for any list answer.

### Guards
- **Props stay TILE occupants** (project-format line 1020): no unit id, no side, no HP, not UNIT-targetable, never in loadouts or pools. `Resolution` is not changed to count a prop as a unit.
- **check-law:** the game words (`pickaxe`, `hoe`, `axe`, `sword`, `mine`, `plough`, `chop`, `rock`, `ore`, `tree`) appear only in catalogue data, presets and `src/rules`, **never in `src/core`**.
- **Data and presets only.** The presets are catalogue data; no item, tool or action is hard-coded in the format.
- No ids reused: list item ids, preset ids and event names keep their meaning forever.
