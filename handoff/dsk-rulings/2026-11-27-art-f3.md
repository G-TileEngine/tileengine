# DSK rulings: art pack format (F3a/F3b), 2026-11-27

Asked by: Engine Architect, 2026-11-27 03:58 (overhaul plan main ac39c690, docs/maker/ux/maker-overhaul-plan.md § EA-7.4).
Base: project-format r41 (7d89c4f4). No new fields, no core-types change, no version bump, no migration.

## A1. ART2 pack origin and credit
- `origin: {kind: "upload", fileName: "<name>.png"}`. **No `bakedFrom`.** `bakedFrom` already has one meaning and one shape (project-format L656: `{assetId, painter, paintStyle?, recipes, cellMap?, at}`, pointing at an in-project source asset). tools/art-bake is outside the project, so reusing the key would give it a second meaning.
- Not `origin.builtin`: the pack is demo-template content, not the v1 built-in library (Kenney-only, §6.2.4 r14).
- `credit: {author: "RaiKynn", license: "LicenseRef-TileEngine-Own", source: "own, procedural", aiGenerated: false}`, the existing studio-own procedural case (§6.2.4 r13 table). Use the exact string `"own, procedural"`; "own, procedural (code-made)" would be a third source string (§6.2.4 allows two). No `status` (final).
- Link to the bake manifest: **nothing stored in the project.** The asset id is the content hash, so tools/art-bake/pack-manifest.json keys each entry by asset id; that is the link. No `credit.url` (it's for public URLs) and no new field.
- `maskSet` stays derived, never stored (PS11). `tile`, `grid`, `clips` (`<action>-<facing>`), `tileProps.anim` and `tileProps.logic` are stored as usual for an upload tileset/sprite (§6.2).

## A2. Ground from logic
- **The maker writes layer tiles; nothing is derived at draw time.** This is the r7 PL13 rule already in §6.4: `layers[].autotile?: 4 | 8` is an editor hint, masks are computed by the editor brush, "never stored, never recomputed at runtime". Logic and visuals stay separate (K3); Render and the runtime don't change.
- The brush picks the tile from `logic.terrain` → `logic.palette` → the tileset's `tileProps[i].logic`, plus the blob47 mask, and writes the index into `tiles`. "Re-tile layer" rebuilds a whole layer the same way.
- The F3b demo ships with its ground layer filled: `tileset: <pack tileset id>`, `autotile: 8`, every `tiles[i]` written by the template build.
- `null` in `tiles` keeps its one meaning, an empty cell, whatever `tileset` is. "Tileset set, tiles null" is not a derive switch. A draw-time mode would need a new explicit field and a runtime autotiler against PL13; not ruled in, not needed for F3.
- Existing projects with `tileset: null` keep drawing no ground (background/letterbox shows). Nothing is rewritten on load or save.

## A3. Tile size
- `map.tile` stays `null` (inherit) in the demo. The 32 px value goes in **`settings.tileSize: 32`** (§3.1, the project default; `null` map.tile inherits it, one source). Set `map.tile` only for a map that must differ.
- F3a: the demo stays as it is (no `settings.tileSize`, so today's reader fallback of 16 applies). F3b writes `settings.tileSize: 32` into the template only. Note: 16 is outside the 32–128 warn range, so the current demo should already warn; 32 clears it.
- **No version bump and no migration.** `settings.tileSize` and `map.tile` are existing fields; this is template content. tile-project stays v6, map stays v5. Existing projects are never rewritten; a project without `settings.tileSize` keeps the fallback 16.
- r42 records: absent `settings.tileSize` (legacy and the pre-F3b demo, against "always stored") resolves to 16, and the reader reports it per Law 12.
