# DSK rulings: steps 10b–11a (2026-11-25/26 London), for the EA's step guides 10b (b38b56cc), 10c (f4f065ed), 10d (2aaf757b) and 11a (d2402180)
Base: project-format r41 (7d89c4f4, on main fddf499b). No doc change, version bump, migration or CN here; every line below goes into project-format r42.

## E1. Row encoding (10b Q1)
- A row is `{code, where, detail: string}` (§16 types). `where` is the doc path plus a JSON pointer to the entry, or the `fileName` for import-time rejects (nothing is written yet).
- `detail` is the remaining field as a bare string when there is one, else `JSON.stringify` of the remaining fields in documented key order.
- So: `uploadTooLarge` where = fileName, detail = `{"w","h","max"}`; `uploadTypeUnsupported` where = fileName, detail = the sniffed type; `advancedRenderInactive` where = path, detail = `pixelPerfect` | `fit`.

## E2. Effect ids in rules (10b Q2, 10c Q1)
- An id in `project.rules`, `stage.rules`, `unit.setupIds` or `neutrals[].setupIds` that resolves to nothing is H3 (broken reference), unchanged.
- An id there that resolves to an `effects/` doc (including a legacy `setup_<ULID>` one) is warning **`effectNotRule`** (new), ignored, never H3 (§6.7 L1152, §13). The resolver checks `ProjectStore.effects` before calling H3.
- `where` uses the same pointer as H3 at that site (e.g. `stages/<id>.json#/rules/0`); detail = the effect id.

## E3. Version check on `effects/` (10b Q3)
- `effects/` docs are `behaviour-setup` v3: the same formatVersion guard and chain as `setups/`, and the same newer-than-app path (§12).
- "Never refused" in §6.7 Ids (D22) covers id shapes only, not versions.

## E4. Built-in effect answers (10c Q2, 10d)
- An `effect` answer stores the **bare** BTF id (`"btf-holy-blade"`, setup-format L454). `builtin:effect/<id>` is only the `presetRef.presetId` namespace (L446/L455), never an answer value.
- Resolution order: `"none"`, then an effect doc id, then a bare BTF id against the slice's `effect` presets (§7.2 5a), then `unknownRef` (plays as `none`).
- Readers accept `builtin:effect/<id>` in an answer as a silent alias (no row, never rewritten). Writers always write the bare id.
- An id the slice resolves but that isn't in that knob's `ref.builtin` list still plays, with warning **`builtinNotListed`** (new), where = the answer's pointer, detail = the id. Writers only offer `ref.builtin` ids (10d Q3).
- Any non-`none` `effect` answer, a saved-effect pick included, puts `effect` (with its presets) in the slice (§4); any `effects/` doc does too. A project on another `catalogue_rev` goes through writer drift in memory (setup-format §8.2, §12); a built-in id the new rev lacks is `unknownRef` (10d Q1).
- A null catalogue default means unset (D19). A preset override with a value replaces it; a preset override of null is also unset. Merge per field; null never deletes an answer (10d Q2).

## E5. Export MVP exception (11a Q1)
- Format §11.1 L1551 ("exported games never contain project documents") and §7.2 describe the step 36 Render target. Roadmap L86 scopes the step 11 MVP to bundle the saved project's files. **The MVP is an allowed exception until step 36**, which supersedes it. Conditions:
  - (a) Ship only the saved tree minus `effects/.deleted/`, `notes/`, `sprite-recipes/`, `.tmp`, and any `.deleted/` trash folder.
  - (b) Documents are the exact bytes the save just wrote: never re-serialised, stripped or patched.
  - (c) The game reads them as current-version documents only. Readers never migrate: a non-current doc is a typed `needsMigration` refusal and that stage doesn't play. No `migrations/` code and nothing from `@te/project-write` enters the game zip (an audit fail).
  - (d) It is a private test build. Nothing public without CEO SEND.

## E6. Export MVP scope (11a Q2–Q4)
- Q2: no §7.2 closure until step 36. Unselected stages and unused files ride along, but the game offers only the stages Test would play.
- Q3: no `export.audit.json` until Render (step 36). The build-time checks in tests suffice. No new `build.json` fields for this.
- Q4: INTERNET in 11b is the EA's and QA's call. Data side: nothing in the bundle needs the network (`extensions.online` is PROPOSED, no module), so the DSK leans to dropping it if the device check passes.

## E7. E5 clarified (2026-11-26 09:1x, QA's 11a trial via CoS)
- **E5(c) means write-side code only.** The pure in-memory read-up already in main's play release (`src/project/load/migrate.js`: tile-project v4/5, map v4; D9) may ride in the game zip. It never writes, and step 36's Render drops it. Still banned: `@te/project-write`, `migrations/<kind>/` write steps and anything that writes files.
- **No refusal on `migrated` rows (amended 09:2x after QA's code check; replaces the 09:1x guard).** Main's save (`planSave`) writes only the edited docs, as stored, and never persists the read-up, so D9's "written on the next save" isn't true in code yet. The MVP game therefore reads old docs exactly as Test does: the verbatim saved bytes (E5(b)), read up in memory by `load/migrate.js`. Build game doesn't refuse them, and the zip may hold v4/v5 docs. A doc newer than the engine, or one the read-up can't bring current, is still the typed `needsMigration` refusal. Upgrade-on-save (D9 in code) is not 11a scope; it's backlog for the EA, and step 36's Render removes the read-up from games.
- **Audit:** banned are `@te/project-write`, `migrations/<kind>/` write steps and any file writing. `load/migrate.js` is allowed. Gate check: a v4 project built straight after opening plays to the same result in the zip as in Test.
- **E5(b): drop `safe()`.** Escaping U+2028/2029 doesn't change any value, but it rewrites the saved text, and ES2019 allows both raw in strings. The files module carries the saved text unchanged.
