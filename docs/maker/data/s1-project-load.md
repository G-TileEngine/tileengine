## 1. Goal
The play stage stops running the hard-coded `DEMO_LOAD`. It reads `fixtures/demo.tileproj/` through one pure `readProject(files)`, and with the same seed it plays exactly like today. This is stage 1 of the agreed order: format, reader, validation and versioning first, then the maker.

## 2. Scope
**In:**
- `readProject`, which runs one migration function in memory, checks, and reports. It never throws, never writes and never deletes.
- `playDocsOf` in `tools/play-stage/project.ts` (not `src/`), an adapter from a read project to the existing `PlayDocs` / `docsToInput` path.
- Aligning `src/project/read/unit.ts` to §6.3 (Q3).
- The fixture, the tests below, and deleting `DEMO_MANIFEST`, `DEMO_MAP`, `DEMO_STAGE`, `DEMO_SETUP`, `DEMO_TALK` and `DEMO_LOAD`.

**Out (deferred):** `assets`, sprite-recipes, paint-styles, effect documents (only the builtin `none` and `btf-*` are referenced), decks, notes, achievements, audio, presets, `index`, saving, the export closure, catalogue drift, and H1/H4/H6. When these are absent, behaviour is today's, so no migration is needed.

**No new format.** The minimum project is a strict subset of project-format r40. There are no new fields, no CN and no version bump. The phone-test input bugs (targeting, second action, pan-then-select) belong to EA and QA, not to S1.

## 3. File layout (one game = one folder, §2)
```
fixtures/demo.tileproj/
  project.json                                   tile-project v6 (§3.1)
  catalogue/slice.json                           catalogue-slice v1, rev 28 (§4), generated, never hand-edited
  maps/map_01JDAM00000000000000000001.json       map v5
  stages/stage_01JDAS00000000000000000001.json   stage v2
  units/unit_01JDAN0000000000000000000{1..7}.json unit v2 ×7
  setups/setup_01JDAT0000000000000000000{1..5}.json behaviour-setup v3 ×5
```
- **Ids** are `<kind>_<ULID>`. The fixture ULIDs are fixed, valid Crockford base32 (26 characters, no I/L/O/U, first character ≤ 7), and readable by design.
- **Id table:**

| Unit / setup | Id |
|---|---|
| Knight / Archer / Cleric / Wolf / Villager / Crate / Merchant | `unit_01JDAN…01` / `…02` / `…03` / `…04` / `…05` / `…06` / `…07` |
| talk (villager) / ability-presentation / unit-roster (army) / archer basic-attack / archer line-shot | `setup_01JDAT…01` / `…02` / `…03` / `…04` / `…05` |

- **`files` keys** are POSIX paths relative to the `.tileproj` folder. Any other path is an unknown file: it is kept and reported as a warning (§2).

## 4. Fixture JSON (exact)
Every file is UTF-8 with LF line endings and one trailing newline. Timestamps are fixed. `history` is `{cap: 200, baseSeq: 1, ops: []}`, meaning the creating op was compacted (setup-format §4 rule 7: history is never needed to load). In every answer, `defaultRef.rev` is that knob's catalogue rev 28 `rev`.

### catalogue/slice.json (generated)
The slice is generated by `tools/project/slice-of.ts`, a pure function of `behaviours.json` rev 28 (sha256 `e182b094…`) and an id list. It's about 3.2k lines, so it isn't inlined here. Its shape is exactly:
```json
{"kind": "catalogue-slice", "formatVersion": 1, "schema_version": 3, "catalogue_rev": 28, "gates": "<catalogue gates, copied whole: uses-card-hand, uses-menu>", "behaviours": "<entries below, catalogue order>"}
```
- **`behaviours`** holds, in catalogue order: `ability-presentation`, `basic-attack`, `line-shot`, `barrier-line`, `adjacency-synergy`, `unit-roster`, `talk` and `terrain`.
  - That's the five used by setups, plus `barrier-line` and `adjacency-synergy` (`@` deps of `line-shot` knobs `barrier_blocks` and `pair_doubles`), plus `terrain` (`closure: "always"`).
  - `effect` isn't included, because every `effect` answer is `none`.
- **Each entry is verbatim, minus** `sources`, `variants`, `used_by`, `conflicts`, `needs_reverify`, `knobs[].default_source`, `item_cites` and `item_sources` (§4).
- **Serialisation:** `JSON.stringify(slice, null, 2) + "\n"`.
- **Test:** a test regenerates the slice and asserts it is byte-equal to the committed file, which keeps the fixture honest.

## 5. Mapping from DEMO_LOAD
| Today (`load.ts`) | Project home | Notes |
|---|---|---|
| `DEMO_MANIFEST.project` (`id "demo"`, `catalogueRev 1`, `stages`, `rules []`, `loadout`) | `project.json` | The id becomes `project_<ULID>` and `catalogueRev` becomes 28. `rules` holds the required `ability-presentation` setup (H1 home) and the army `unit-roster` setup. `difficulty` and `render` take the §12 defaults, `assets` is `{}`, and `index` is absent (computed on save). |
| `DEMO_MAP` (`map-6x9`, terrain, palette `{0 floor, 1 water, 2 rock}`) | `maps/map_….json` | Terrain ints are unchanged. **`rock` becomes `wall-block`**, the canonical blocking wall (§6.4), because `rock` isn't a `tile_types` id and would play as `floor` with a warning. One empty `ground` layer is added (§6.4: at least one layer). |
| `TILES` (3 hand rows) | none (catalogue) | Tile meanings come only from `terrain.tile_types`. With no terrain setup, the adapter takes `installOne(TERRAIN, {}).tiles` (the engine's catalogue table). `water` and `wall-block` are not open and push can't enter them, the same as today's rows. |
| `DEMO_STAGE` | `stages/stage_….json` | Placements, facings, `seed 24301`, `sides.enemyPool "wolves"` and the merchant's `side "player"` are kept 1:1. **The top-level `setupIds: ["talk-villager"]` isn't a format key.** It moves to the villager's `neutrals[].setupIds` (D2, DECIDED r40). The stage's loadout equalled the project's, so it's stored as `null` (one source, §6.5). |
| `RECIPES[].name` | `unit.name` | Knight, Archer, Cleric, Wolf, Villager, Crate, Merchant. |
| `RECIPES[].id` (starter sprite) | `unit.sprite: null` | **Play-stage fallback only:** while the sprite is null, `board.ts` picks its starter picture by `unit.name`. This stays in tools/ and is never stored. |
| `RECIPES[].team` | placement side | Units have no side (§6.3): the loadout is `player`, the pool is `stage.sides.enemyPool` = `wolves`, neutrals are `neutral` and the merchant is `player`. `TEAM` colours become keyed by side, which gives the same colours as today. `wolves` is a real side because the fixture's `ability-presentation.team_colours` lists it with today's hex values (§6.5 Sides). S1 paints from `TEAM`; reading `team_colours` is a later slice. |
| `DEMO_SETUP.base {hp 9, atk 1}` | `unit-roster.unit_hp` / `unit_atk` (army setup, catalogue defaults 9 and 1) | That's the "army value" of §6.3. |
| `DEMO_SETUP.stats` | `unit.stats.unit_hp` / `unit_atk` as `{value, rev}` | Only values that differ from the army value are written (the §12 import rule), so the knight is `{}`. The adapter fills in all seven. |
| `DEMO_SETUP.hitClass "basic"` | `damage-resolution.hit_class` catalogue default `basic` | There's no setup. The adapter emits `"basic"`, and line-shot hits stay `spell` (engine `battle.ts`). |
| `DEMO_SETUP.reach {archer 3}` | archer `basic-attack`: `reach_mode custom-cross`, `custom_ns 3`, `custom_ew 3` | For units without a basic-attack setup, the engine's default reach of 1 applies, as today. |
| `DEMO_SETUP.abilities.archer [{reach 3, damage 2, effectRef "line-shot"}]` | archer `line-shot`: `range 3`, `damage 2`, `caster_class archer` | The adapter builds `{reach: range, damage, effectRef: "line-shot"}`. `effectRef` is the behaviour id the engine matches, not an effect document. The setup's own `effect` answer stays `none`. |
| `DEMO_TALK {"talk-villager": "Hello, traveler."}` | `talk.line` user answer `"Hello, traveler."` | The demo spelling is kept as the user's answer, which differs from the catalogue default `"Hello, traveller."`. The adapter emits `talk["talk-" + unitId]` for each neutral that carries a talk setup. |
| `DEMO_SEED 24301` | `stage.seed` | `hostSeed` = `stage.seed`. |
| `chosen ["knight","archer"]` (hard-coded in `docsToInput`) | runtime (§6.6) | It's derived as `required`, then `roster` order with no duplicates, cut to `min(size, playerSpawns.length)`, which gives knight and archer. |
| `DEMO_LOOKS` (canopy, braziers) | none in S1 | It's dropped from data. It comes back later as `map.objects[]`, never as a `looks` field. See Q1 for the looks tests. |

**Adapter rules (EA 2026-11-18, main `f2df5c40`):**

## 6. Reader contract
Code for `readProject` and `migrateProject` goes in `src/project/load/` (new). This is the load layer shared by the future maker and the play host. `createWorld` and `src/project/read/` still read only current versions and never migrate (D3 is unchanged for the sim), apart from the Q3 alignment of `src/project/read/unit.ts`. `playDocsOf` lives in `tools/play-stage/project.ts`, not in `src/`: `src` never imports `tools` (`BUILD_GUIDE.md:64`), and the adapter builds play-stage keys (`talk-*`, `effectRef`).
```ts
export type ProjectFiles = Readonly<Record<string /* posix path in .tileproj */, unknown /* JSON.parse result */>>;
export type Severity = "hard" | "warning" | "info";
export type ReportRow = { readonly code: string; readonly severity: Severity; readonly path: string /* file#json/pointer */; readonly detail?: string };
export type ProjectStore = {                 // §16 "store"; documents as stored (after in-memory migration), unknown keys kept
  readonly manifest: ProjectManifest;        // §16 shape; index absent or ignored
  readonly slice: CatalogueSlice;
  readonly maps: Readonly<Record<string, GameMap>>; readonly stages: Readonly<Record<string, Stage>>;
  readonly units: Readonly<Record<string, Unit>>; readonly setups: Readonly<Record<string, BehaviourSetup>>;
  readonly unknownFiles: Readonly<Record<string, unknown>>;
};
export type ProjectLoad =
  | { readonly ok: true;  readonly readOnly: false; readonly project: ProjectStore; readonly report: readonly ReportRow[] }  // no hard rows
  | { readonly ok: false; readonly readOnly: false; readonly project: ProjectStore; readonly report: readonly ReportRow[] }  // hard rows: shown, not playable
  | { readonly ok: false; readonly readOnly: true;  readonly project: null;         readonly report: readonly ReportRow[] }; // refusal row first
export function readProject(files: ProjectFiles): ProjectLoad;              // pure; never throws; never mutates `files`
export function migrateProject(files: ProjectFiles): { files: ProjectFiles; report: readonly ReportRow[] }; // §7; the ONE chain
```

`playDocsOf` (in `tools/play-stage/project.ts`, S1b; same ~65 lines):
```ts
export function playDocsOf(p: ProjectStore, stageId?: string): PlayDocs & { chosen: readonly string[]; tiles: readonly CoreTileType[]; names: Readonly<Record<string, string>> };
```
- **`readProject` order:**
  1. Find `project.json`. If it's missing or not an object, refuse with `notAProject`.
  2. Run the version gate on every known document (§7).
  3. Run `migrateProject`.
  4. Do a structural read and run the checks (§8).
  5. Build the store.
- **Rows** are sorted by path, then code, so the report is deterministic.
- **§16 alignment:** `readProject(files) → {store, needsMigration[]}` in §16 becomes this `ProjectLoad`. The store is `project`, and each `needsMigration` entry is an info row `migrated` (`detail "tile-project 4→6"`). §16 gets updated to match when this is adopted (r41).
- **`playDocsOf`** uses the first `project.stages` entry by default. It throws only if handed a store whose load was not `ok`, because hosts must check `ok` first. It may call `readProject` output but must not `JSON.parse` or read `formatVersion` / `kind ===` itself (P2).
- **S1b boot:** `tools/play-stage` runs `readProject` synchronously at boot. If the load isn't `ok` or is `readOnly`, it shows the report rows, starts no match and never throws.
- **Seams:** `docsToInput` (`load.ts:36-38`) gains `chosen` and `tiles` inputs. S1b builds on main after S0 merges (both edit `match.ts` and `board.ts`). `createMatch()` with no docs must keep working for S0's tests. S1b deletes the villager fallback at `match.ts:84` (D2).

- **Unknown keys** in known documents are kept as stored (§2 R4) and carried into the store. **Unknown files** are kept in `unknownFiles` and reported as `unknownFile` warnings.
