## Goal
In an opened project, the user taps a stage and gets the **stage editor**: a phone-size preview of the stage's map. They tap a tile, an **Add here** sheet opens, and they pick what goes there. In 4a that is ground or terrain. In 4b it is also a Your-team start, an NPC or an enemy, and after an NPC is placed, a **What do they do?** sheet. In 4c they add, rename and delete stages, and rename, resize and delete maps. Every change is saved to the project's own files. **Test** then plays the edited stage in the real play stage. The maker only writes data; the engine runs the rules.

## Rules this step must keep (all three runs)
1. **No button before it works (roadmap rule 2; shell-lessons #1 rule 2).** Every row in every sheet is wired to real data that the play stage really plays. An option that isn't wired is **left out, not greyed**. Step 2's greyed Test is the only named exception, and it is gone by now. Building, Lair sets, Lava, Wander, Seller, Quest giver and Hostile are not shown in step 4.
2. **The maker only authors data, and the engine runs the rules (roadmap rule 1).** The editor writes `map.logic.terrain`, `map.logic.palette`, map size, stage placement entries, stage and map names, and setup documents. It never decides what a tile does, who wins, or how a unit acts. What a tile type means comes only from the catalogue's `terrain.tile_types` (project-format §6.4). The editor may read that data (for example a type's `open` flag) to label or hide a choice, but it never re-implements a rule.
3. **File names.** Every document file is `<kind>_<ULID>.json` (Crockford ULID, 26 characters); only `project.json` and `catalogue/slice.json` have fixed names. A new document gets a new id and file (`setup_<ULID>`, `stage_<ULID>`, `map_<ULID>`). Never reuse an id (step 2 Rules 2). **Rename changes the `name` label only, never an id or a file name.**
4. **New documents come from `.json` skeletons, not code (D10 (was R-D1)).** A new document is copied from a whole-document `.json` skeleton under `data/templates/` and then filled in. The code fills in only ids, names, `catalogue.rev`, answers and placements; it never writes a `kind` or `formatVersion` literal. Only `.json` files go under `data/templates/`. Each skeleton loads through its reader in a named test.
5. **Setups store only knob values that differ from the default, and attach through `setupIds` (roadmap rule 4; D16 (was R-D7)).** A new setup lists every knob of that behaviour in the slice that has a catalogue default, as `{source: "default"}` with no `value`. A knob with a `no_default_reason` stays absent. Only a knob the user set gets `source: "user"` and a `value`. The knob list comes from the slice, never from a list in code. An NPC's setup attaches through that placement's `neutrals[].setupIds`, never through a new field.
6. **Import direction and the one parser (EA ruling 2026-11-18, step 3).** The maker imports the play stage; the play stage never imports `tools/maker` or anything under `src/editor/`. The editor gets documents from step 2's store as parsed objects and never calls `JSON.parse` (the one `JSON.parse` in `tools/maker` stays in `project-files.ts`). The P2 scans in `tests/project/load/one-parser.test.ts` stay as they are. No `formatVersion` or `kind ===` in `tools/maker` or `src/editor/stage`.
7. **Stamped builds (step 2 Rules 3).** New maker files ship under `<out>/maker/<stamp>/`, and the play stage under `<out>/play-stage/<stamp>/`, through the existing `tools/maker/build.ts`. `index.html` is the only unstamped file. Do not add a second build.
8. **Every change is saved, and every failure is shown (Standing lessons; step 2 Save rules).** Edits go through step 2's save plan and store: changed docs only, `rev + 1`, tmp then rename, `project.json` last. A failed save shows the typed error in words, and the old files stay intact.
9. **Start new / Clear all ships with this tool (roadmap rule 8; shell-lessons #6 (a)).** The CEO's rule: a **Start new** button sits **beside View**, with a warning, in this tool. It ships in 4a, working. It is never shown before it works.
   - **Proposed UX answer (Editor & UX Designer, not a CEO rule):** Start new is one Undo step, so the user can take it back right away.
10. **No unit on a closed cell (EA R-E4).** The editor never offers a closed type (`open: false` in the slice's `tile_types`) on a cell that has a unit, and never places or moves a unit onto a closed cell. The reader side (built in 4a, see **Reader side on main** below): `readProject` gives a **warning** row (not hard) for a placement on a closed cell or outside the map. The engine already skips that placement in memory. The row is **D17 `placementDropped`**: a warning, never hard, with `{stageId, list: "playerSpawns" | "neutrals" | "enemyPool", index, unitId?, sq, reason: "closedCell" | "outsideMap"}`. The reader skips that placement in memory and never writes back. The editor writes a drop only on a confirmed resize (4c), one row per entry. Step 7 link cells will add a reason value later, not a new code. A dropped NPC placement's talk setup stays on disk (D11).
11. **History is kept, not grown (D12 (was R-D3)).** Undo is session-only. Any `history` already in a stage, map or setup document is written back unchanged. The editor appends no ops. **Known gap:** setup-format §4 rule 2 asks for an op per change; appending ops is deferred to a later step.
12. **Shared maps are painted in place (D15 (was R-D6)).** Many stages may share one map (`mapRef`). The editor paints that map, with a note that says how many stages use it. It never makes a silent per-stage copy. A "copy map for this stage" fork is later work.
13. **Hostile stays off (shell-lessons #1 rule 4; EA R-E5).** The editor writes no `side` on a `neutrals[]` entry. An NPC with no `side` plays **neutral**: it can't be targeted, it doesn't act, and it isn't counted for a wipe. There is no Hostile control in step 4. A later Hostile toggle will write `side` on that `stage.neutrals` entry, set to `stage.sides.enemyPool ?? "rival"`, with no new field. It ships with or after S0b.
14. **Words, not only colour.** Each preview cell shows its type in words or a letter as well as a token colour, so colour is never the only cue (AA contrast, 48 px targets).

## Reader side on main (checked on `772f7aa2`)
Read this before the D17 (4a) and D21 (4c) rows. Line numbers are on `772f7aa2`; re-check them on each run's base.
- **Two layers.** `readProject` (`src/project/load/read-project.ts`) gives the **report rows** the maker shows. The **engine** reads the same raw documents again when a match starts: `createWorld` (`src/sim/world.ts` lines 29–66) calls `readMap` (line 36), `readStage` (line 37) and `resolvePlacements` (line 58), then `units.place` for each placement (line 59). The play stage reaches it through `openProject` → `playDocsOf` → `docsToInput` (`tools/play-stage/load.ts` line 21).
- **Placements: the engine already skips.** `src/project/read/placements.ts` `resolvePlacements` (lines 17–45) owns placements. Its `push` (lines 9–12) skips a placement outside the map with a `spawnOffMap` notice (line 10: `{code, message, at}`). `src/core/unit/units.ts` `place` (lines 36–46) then refuses a closed cell with a `placeClosed` notice (line 39, through `deny` at lines 33–35), and `placeOffMap` (lines 37–38). So the in-memory skip for both D17 reasons exists today. **What is missing is the report row:** `readProject` never resolves placements. `readProject` is pure: line 73 says it never writes and never mutates `files`. Its `refs` (lines 22–38) only checks that `neutrals[].unitId` (line 34) and `enemyPool.entries[].unitId` (line 35) exist.
- **Edges: the engine already skips.** `src/project/read/map.ts` `logicOf` (lines 11–18) reads `logic.edges` (lines 15–16) and accepts any whole-number `c`, `r`, with no bounds check. `src/core/grid/grid.ts` lines 53–55 then skip an off-map edge with an `edgeOffMap` notice. `readProject`'s map branch (lines 90–97) checks only the `terrain` and `layers[].tiles` lengths (`terrainLength`, lines 95–96). **What is missing is the report row.**
- **Lanes are not entries.** `logic.lanes?` is an optional per-cell `int[]` of length `cols*rows` (project-format §6.4, lines 948–953; `src/types/core-types.ts` line 89). No reader reads it: `logicOf` returns only `terrain`, `palette` and `edges` (line 17). A wrong length is a warning, and the array is ignored (format line 953). So a resize **crops** lanes like terrain (4c Rule 7); there is no lane entry to drop.
- **Row pattern.** Today's out-of-bounds notes are engine `Notice`s (`src/core/notice.ts` line 4: `{code: string, message, at?}`). The maker sees `ReportRow`s (`src/project/load/types.ts` line 4: `{code: string, severity, path, detail?}`), made by `row()` (`read-project.ts` line 8), the same way as `unknownRef` (line 69). The new rows follow `row()`: severity `"warning"`, the D17 or D21 fields carried by `path` (the JSON pointer names the stage or map file, the list and the index) and `detail` (the reason). `unitId` and `sq` are read from the entry at that path. No change to the `ReportRow` type.
- **No code union to edit.** Both `ReportRow.code` and `Notice.code` are plain `string`. Nothing in the code lists the allowed codes. The code table lives in the docs: `docs/maker/data/s1-project-load.md` §8 and project-format r41's report-code table (DSK adds D17 and D21 there).
- **Closed comes from the slice.** `readProject` already walks the slice's `terrain.tile_types` (line 48) but keeps only the ids. The D17 check needs each type's `open` flag too. A palette int with no key, or an unknown id, counts as Floor (`core-types.ts` lines 86–87), so it's open.

### 4a Behaviour
- **Open:** the opened-project screen (step 2) lists the project's stages by name, each as a 48 px row. Tapping one opens the stage editor on that stage and its `mapRef` map.
- **Top bar:** Back (to the project screen), the stage name, **View**, **Start new**, and **Test** (primary).
- **Preview:** a grid of cells, `cols` × `rows` of the stage's map, each at least 48 × 48 CSS px. A big map scrolls inside the preview. Each cell shows its tile type's label (or its first letter when the cell is small) on a token fill: Floor `--surface`, Water `--accent-soft`, Wall block `--line`, Path and Dirt `--warn-soft`, and any other type `--surface-2` with its label. Cells with a placement (`playerSpawns`, `neutrals`, fixed `enemyPool` entries) show the unit's name initial and a side pill. In 4a placements are shown, not edited.
- **Shared map note (Rules 12):** if more than one stage uses this map, a one-line note under the top bar says "This map is used by N stages. Painting changes all of them."
- **Tap a tile:** an **Add here** sheet opens, titled "Add here" with "Tile c,r". In 4a it has two groups (EA R-E2):
  - **Ground:** Floor, Path, Dirt.
  - **Terrain:** Water, Wall.
  The row labels come from the catalogue's `terrain.tile_types` labels in the project's slice. A row whose id is not in that list is not shown. On a tile that has a placement, closed types are not shown (Rules 10), and the sheet says "A unit stands here" above the rows. No Lava (EA R-E2: no Lava before a hazard step, after stealth).
  - **Path and Dirt only if they fit.** The play stage draws only `water` and `wall-block` apart from ground today (`tools/play-stage/looks.ts`, line 46). Path and Dirt need a tile-id-to-ground-frame table and two new ground frames (see Build). If 4a's total would pass 400 counted lines with them, leave Path and Dirt out of 4a (hidden, not greyed), say so in the hand-back, and 4b adds them. If 4b can't fit them either, they stay hidden.
- **Paint:** picking a row paints the tapped tile and starts a painting run. A chip at the bottom says "Painting Water · Tap more tiles" with **Done**. Each further tap paints that tile, with the same closed-cell rule. **Done** ends the run and saves. A run is one Undo step.
- **Data written by a paint:** `map.logic.terrain[r * cols + c]` gets the palette int for that type id. If the type id is not yet in `map.logic.palette`, add it under the smallest unused int. Never remove or renumber existing palette entries. The map doc gets `rev + 1` and `updatedAt` on save; its `history` is written back unchanged (Rules 11). Visual `layers[].tiles` are not touched.
- **Undo:** a 48 px **Undo** button above the chip. It undoes the last run or Start new, newest first, and saves. With nothing to undo it is disabled and says "Nothing to undo". Undo lives for this editor session only (D12).
- **View:** a small menu with one toggle, **Grid lines: On / Off**. Off hides the cell borders; selection still shows. It is never written to the project. It lasts for the session only; it moves to device-local `editor-prefs.stageView.gridLines` in a later step (D13 (was R-D4)).
- **Start new:** beside View. Tap it: a warning sheet says "Start this stage's ground fresh? Every tile goes back to Floor. Units and NPCs stay. You can Undo this." with **Start new** (danger style) and **Cancel**. Confirm sets every `logic.terrain` cell to the Floor int (adding `floor` to the palette if missing), saves, and is one Undo step. In 4a Start new clears ground only; 4b extends it to placements.
- **Test:** saves, then opens step 3's Test flow with this stage's id (`?stage=<stageId>`). The play stage plays the edited map. Back to maker returns to the stage editor.
- **Errors:** a failed save shows the step 2 typed error in words and keeps the edit on screen with the unsaved dot. A readOnly project opens the editor read-only: the banner says why, and the sheet, Start new and Undo are not shown.

## 4c: stages and maps

### 4c Goal
The project screen lets the user add, rename and delete stages, and rename, resize and delete maps. A new stage can get its own new map, so a game can have two floors (for example a shop downstairs and a home upstairs). The stairs link that joins them is step 7. Every change is saved, and Test plays any stage.

### 4c Read first
Everything in the shared Read first, plus:
1. `docs/maker/data/project-format.md` §3.1 (`project.stages`, `render.excludedStages`), §6.4 (`cols`, `rows`, `layers[].tiles` length `cols*rows`, `logic.terrain` length `cols*rows`, `logic.edges`, `logic.lanes?`; the editor warns above 256×256), §6.5 (`mapRef`: many stages may share a map).
2. `docs/maker/roadmap.md` MS-03 step 7 row (doors, stairs, gates; the two-floor shop).
3. Step 2's `data/templates/empty.tileproj/` (its stage and map files are the skeletons for a new stage and map).

### 4c Rules
**EA conditions (EA ruling, 2026-11-19).** EA set three conditions, and 4c is what makes the two-floor shop possible (two stages, each with its own map; the stairs are step 7):
1. **Rename changes the label only.** Renaming a stage or a map changes its `name`, never its id or file name.
2. **Delete is refused while something points at it.** Deleting a map that any stage's `mapRef` uses is refused with a row that names the stages. Deleting a stage or map that a link targets is refused the same way. The format has no link field yet (links arrive in step 7), so 4c writes the check as one pure function, `refsTo(id)`. In 4c it covers `mapRef` only, and the hand-back names the step 7 carry: step 7 extends `refsTo` with link targets.
3. **Resize warns, then drops with a row.** A resize that cuts off a placement (or, from step 7, a link cell) warns first and lists what will go. On confirm it drops those entries and writes one **D17 `placementDropped`** row per dropped placement, with `reason: "outsideMap"` (Rules 10). A dropped NPC placement's talk setup stays on disk (D11). `logic.edges` entries outside the new size are listed in the same warning. On confirm each one is dropped with one **D21 `mapEntryDropped`** row: a warning, never hard, with `{mapId, field: "edges", index, reason: "outsideMap"}` (D21 as amended, doc `aacb7e01`; D21 text unchanged from `24cba61e`), one row per entry. It works like D17: the editor drops entries only on a confirmed resize, and the reader skips an out-of-range entry in memory and never writes back. `logic.lanes` is a per-cell array, not a list (see **Reader side on main**), so it is cropped like terrain (Rule 7), with `0` in new cells, and gives no row (D21 as amended).

**UX choices (Editor & UX Designer, not EA conditions).** These are design choices for this run. They stay unless CoS or the CEO changes them:
4. **The last stage can't be deleted.** The row says "A game needs at least one stage".
5. **Names are 1–40 code points after trimming**, the same rule as project names in step 2.
6. **New stages and maps are copies of the Empty template (Rules 4).** A new stage and its new map are copies of the stage and map in `data/templates/empty.tileproj/`, with new `stage_<ULID>` and `map_<ULID>` ids, the new `mapRef`, and the names "Stage N" and "Stage N map". No `kind` or `formatVersion` literal in code.
7. **A resize keeps the top-left corner.** Cells inside the new size keep their values. New cells get the Floor int in `logic.terrain`, `null` in every `layers[].tiles` array, and `0` (no lane) in `logic.lanes` if the map has it, so every array stays `cols*rows` long.

**From D11.**
8. **Delete is not hard delete.** A deleted stage is removed from `project.stages` and `project.render.excludedStages`; a deleted map is unreferenced. Their files stay on disk, like orphaned setups (D11). Undo (session-only) restores them.

- **Project screen, Stages section** (the stage rows from 4a): **+ Add stage** at the end of the list. Each stage row gets a ⋯ menu: **Rename**, **Delete**.
  - **+ Add stage** asks one question: **New map** (a fresh map from the Empty template) or **Use map: <name>** (one row per existing map). It then adds the stage to `project.stages` and opens it in the stage editor.
  - **Delete** a stage: removed, with a "Deleted · Undo" toast for 6 s, as in step 2. The last stage shows the refusal instead.

If the new size cuts off anything, a sheet lists each placement and edge that will go, with **Resize anyway** and **Cancel**.

- Every action saves, and is one Undo step for this session.
